# Тикет 18. Ужесточить callback type/date/CRLF validation до любого upstream-вызова

- **Ветка:** `feat/w3-18-callback-validation-hardening`
- **Приоритет:** средний (не блокирует зачёт, замечание сохраняется)
- **Источник:** `week-3-intern-feedback.pdf`, «Средний приоритет: Callback validation допускает malformed values»
- **Порядок доработки:** 3 из 5

## Наблюдение

`python/src/perimeter/callback.py:24-72` — три конкретных дефекта:

1. **CR/LF в конце проходит.** `re.compile(r"^[^\r\n]{1,128}$")` + `.match()`:
   якорь `$` в Python совпадает и перед завершающим `\n`, поэтому
   `"abc\n"` проходит `_NO_CRLF_1_TO_128`. То же для `_NO_CRLF_0_TO_500` и
   `_OCCURRED_AT`.
2. **`occurredAt` проверяется только по форме.** `_OCCURRED_AT` — чистый
   regex по шаблону, поэтому `2026-13-45T99:99:99Z` принимается как валидная
   дата.
3. **`TypeError` на non-hashable `result`.** `if result not in _RESULTS`
   (`:68`) выполняет membership test по `set`; если провайдер прислал
   `"result": {"a":1}` или `["x"]`, Python бросает
   `TypeError: unhashable type: 'dict'` **до** проверки типа. Это не 400, а
   необработанное исключение — HTTP 500 от adapter.

`python/src/perimeter/adapter.py:60-87` вызывает `parse_callback` до
upstream-запроса, поэтому исправление целиком лежит в `callback.py`: всё,
что прошло валидацию, уже уходит на платформу и возвращает 422/503 вместо
адаптерного 400.

## Последствие

Недоверенный legacy-callback пересекает anti-corruption boundary или вызывает
внутреннюю ошибку. Провайдер получает нестабильную классификацию (500 / 422 /
503 вместо 400) и может бесконечно повторять непригодное сообщение.

## Что сделать

В `parse_callback`:

1. **Сначала проверить тип каждого поля**, только потом значение. Порядок:
   `isinstance(..., str)` → regex/членство. Для `result` — сперва
   `isinstance(result, str)`, затем `result in _RESULTS`; это устраняет
   `TypeError` для object/array/null.
2. **Заменить `.match()` на `.fullmatch()`**, а якоря `^...$` — на `\A...\Z`
   (или убрать их при `fullmatch`). После этого CR/LF в начале, середине и
   конце строки отвергаются одинаково.
3. **Добавить реальный разбор даты.** RFC 3339 parser поверх regex-шаблона:
   после совпадения формы разобрать значение (`datetime.datetime.strptime`
   или `datetime.fromisoformat` с нормализацией `Z`), календарно невозможная
   дата → `None`. При этом **исходная строка `occurredAt` сохраняется без
   переформатирования** и попадает в `ValidCallback` ровно как пришла
   (`docs/week3/04-week-3.md`: «исходная строка `occurredAt` сохраняется без
   перепарсинга и переформатирования» — переформатирования, не проверки).

Ни одна из проверок не должна выполняться после первого сетевого вызова:
`parse_callback` остаётся чистой и вызывается раньше `client.post`.

## Как проверить

`python/tests/test_callback.py` (сейчас `:71-107`) — добавить unit-кейсы:

- для **каждого** из пяти полей: значение типа `object`, `array`, `null`,
  `int` → `parse_callback` возвращает `None`, исключение не поднимается;
- CR и LF в начале, в середине и в конце каждого строкового поля → `None`;
- `occurredAt`: `2026-13-01T00:00:00Z`, `2026-02-30T00:00:00Z`,
  `2026-01-01T25:00:00Z`, `2026-01-01T00:60:00Z` → `None`;
- `occurredAt` валидный с дробными секундами → принят, и
  `ValidCallback.occurred_at` **байт-в-байт** равен входной строке.

HTTP-кейсы (`python/tests` для adapter): каждый из перечисленных malformed
body даёт **HTTP 400 с пустым телом**, при этом upstream-клиент не вызван
(мок `client.post` не получил ни одного вызова) и `delivery.inbox` не
изменился.

## Готово, когда

Ни один malformed callback не даёт 500/422/503; все новые кейсы возвращают
400 без upstream-вызова; `uv run pytest` зелёный.
