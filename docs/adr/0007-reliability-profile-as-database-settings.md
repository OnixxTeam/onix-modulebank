# ADR 0007 — Профиль надёжности доезжает до PostgreSQL как database settings

## Статус

Принято.

## Контекст

Бюджет попыток доставки, базовая и максимальная задержка, максимальный jitter, аренда
доставки и аренда job задаются конфигурацией: test profile использует 4 попытки,
200/400/800 мс, jitter 0–100 мс и двухсекундные аренды, обычный профиль — более
консервативные значения. До недели 4 эти числа жили в строке `delivery.retry_policy`,
записанной миграцией 043, то есть менялись только вместе с кодом.

Опубликованная таблица конфигурации адресует все шесть переменных
(`COURSE_OUTBOX_MAX_ATTEMPTS`, `COURSE_OUTBOX_BACKOFF_BASE_MS`,
`COURSE_OUTBOX_BACKOFF_MAX_MS`, `COURSE_OUTBOX_JITTER_MAX_MS`, `COURSE_OUTBOX_LEASE_MS`,
`COURSE_JOB_LEASE_MS`) **только сервису `postgres`**. Это закрывает два очевидных пути:

- миграция не может их прочитать — миграции выполняет `cli`, которому эти переменные не
  адресованы;
- init-скрипт не может записать их в `delivery.retry_policy` — init выполняется до
  применения миграций, таблицы ещё нет.

## Решение

Init-скрипт `db/init/01-reliability-profile.sh` выставляет шесть значений как
database-level settings с префиксом `course.` (`alter database course set
course.outbox_lease_ms = ...`), а функции доставки и захвата job читают их в рантайме через
`current_setting(name, true)`, обёрнутый в `profile.number(name, fallback)` (миграция 048).

`delivery.retry_policy` остаётся **fallback**, а не заменяется: при отсутствующей,
нечитаемой или неположительной настройке функция берёт значение из строки политики и ведёт
себя точно как на неделе 3. Профиль — переопределение, а не новый источник истины.

Jitter вычисляется там же, где `next_attempt_at` — внутри `fail_outbox`. Иначе его пришлось
бы считать в dispatcher, который по [ADR 0006](0006-outbox-inbox-state-stays-in-postgres.md)
не решает ни числа попыток, ни задержек.

Аренда job сохраняет параметр `p_lease_ms`: воркер передаёт значение, которым его
сконфигурировали. Настройка применяется, когда параметр не задан или неположителен, —
именно это делает `COURSE_JOB_LEASE_MS` осмысленной и на стороне базы.

## Последствия

- Значения читаются при каждом вызове, поэтому смена профиля не требует ни миграции, ни
  пересборки; цена — два лишних чтения настройки на вызов.
- Настройки живут на уровне базы, то есть переживают рестарт контейнера, но **не**
  пересоздание volume: они выставляются init-скриптом, который на существующем каталоге
  данных не запускается. Смена профиля на живом стенде — это `alter database` вручную или
  пересоздание volume; для проверяющего прогона, который всегда начинает с чистого
  окружения, это неотличимо.
- Настройка того же имени на уровне сессии перекрывает database-level значение. Это удобно
  в тестах (они так и проверяют профиль), но означает, что сессия может профиль сузить;
  функции валидируют значение, поэтому «сломать» его опечаткой нельзя, только заменить
  другим корректным.
- `profile.number` намеренно молча падает на fallback вместо ошибки: неверная переменная
  окружения не должна останавливать доставку, и диагностируется она сравнением фактического
  расписания с ожидаемым, а не падением.
