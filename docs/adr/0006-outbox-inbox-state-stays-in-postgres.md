# ADR 0006 — Outbox/Inbox и состояние периметра остаются в PostgreSQL

## Статус

Принято.

## Контекст

Python-периметр (`outbox-dispatcher`, `receipt-adapter`, `inbox-reconciler`) стоит между
ядром и реальным провайдером: сеть теряет ответы, порядок сообщений не гарантирован, а
вызов провайдера прямо из action внутри транзакции даёт либо двойной платёж, либо
потерянную квитанцию. Нужно решить, где живёт решение «этой доставке нужен ещё один
повтор» или «это сообщение уже применено» — в Python-процессе или в базе — и как это
разграничение выражено технически, а не только по договорённости между авторами кода.

## Решение

Вся логика доставки — политика повторов, вычисление времени следующей попытки, критерий
«кому эта строка положена сейчас» — живёт в четырёх PostgreSQL-функциях схемы `delivery`
(`claim_outbox`, `succeed_outbox`, `fail_outbox`, `reconcile_inbox`, миграция 039), а не
в Python. `outbox-dispatcher` сообщает базе классифицированный код ошибки
(`*.retryable`/`*.terminal`) и получает обратно готовое решение о следующем состоянии;
он не считает задержки, не решает, исчерпан ли лимит попыток, и не выбирает следующую
строку сам — `claim_outbox` отдаёт её по `FOR UPDATE SKIP LOCKED`. Отвергнута альтернатива
«dispatcher/reconciler держат политику повторов и курсор по Inbox сами» — это сделало бы
периметр вторым владельцем состояния наравне с PostgreSQL, что прямо противоречит условию
недели: единственное место принятия предметных решений — PostgreSQL.

Граница выражена **привилегиями**, а не соглашением: роли `outbox_dispatcher` и
`inbox_reconciler` получают `USAGE` на схему `delivery` и `EXECUTE` только на свои функции
(три — у отправителя, одна — у согласователя), без единого прямого `SELECT`/`INSERT`/`UPDATE`
на таблицы любой схемы, без членства в других ролях и без миграционных прав (миграция 039).
Отвергнута альтернатива «доверять коду периметра не делать DML напрямую» — соглашение
проверяется код-ревью и держится, пока не забудется; привилегия проверяется переключением
роли и попыткой запрещённой операции, и проверка недели буквально так и делает. Компрометация
или баг в Python-коде при privilege-based границе физически не может обойти `claim_outbox`
и записать состояние доставки в обход политики повторов — при conventions-based границе
может.

## Последствия

- Новая логика доставки (иной критерий готовности, другая политика повторов) добавляется
  в SQL-функции схемы `delivery`, не в Python — Python остаётся тонкой оболочкой
  ввода-вывода вокруг чистой функции решения (SPEC: разрез на «чистое решение» и «тонкую
  оболочку» — иначе логика классификации ответов требовала бы фейков базы и сети).
- Любая новая роль периметра обязана получать `EXECUTE` только на свои функции и ничего
  через права по умолчанию для схемы или членство в других ролях — тест прав периметра
  (ticket 09/14) должен расширяться на неё, а не молчаливо доверять новому коду.
- `succeed_outbox`/`fail_outbox`/`reconcile_inbox` обязаны оставаться условными по
  владельцу и версии аренды: устаревший отчёт умершего или перехваченного процесса не
  должен менять состояние — тот же принцип fencing, что и у `finish_job` (ADR 0003), но
  применённый к границе с внешним миром, а не к воркеру.
